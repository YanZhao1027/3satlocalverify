## 先说结论

我们将一份**真实非空 3 变量、1 子句 `x₀` 的 CNF**从前次已完成的 `canonicalStart` 继续输入原版位程序。这一次，**原版数值参数生成、原版两次实际代码搜索、原版行序列化以及各阶段的物理输入／输出搬运和清理，都已运行并正确停机。** 两次搜索生成候选位字，而不是提前写入候选答案。

| 关卡 | 真正执行的原版程序 | 结果 |
| --- | --- | --- |
| **2. 参数生成** | `CodeParametersProgram.fullCommand` | 9,130 条位指令；结果全部正确 |
| **3. 两次代码搜索** | `SparseCodeSearch.graphSearch` 与 `localSearch` | 分别 2,680 和 5,598 条位指令；均停机 |
| **4. 行序列化** | `CodeRowsProgram.command` | 715 条位指令；产生并保存 13 位行数据 |
| **5. 完整装配和初始化** | `NativeCodeAssembly.command`、`NativeLeafPreparation.afterCode` | **尚未完整停机／验证**；已得到真实执行前缀和成本瓶颈 |

**这不是完整 SAT/#SAT 求解器的运行结果，不是 ETH 错误的独立确证，也不是通用 `2^{o(n)}` 时间优势证据。** 这次输入有 `m=1`、搜索图维数 `r=0`，非常简单。

## 1. 真实参数计算和 40×896 物理阶段

原版 `LeafOuterProgram.parameters` 静态指令位置 **4,040**。从上一轮运行后得到的 `m=1`、`B=8` 开始：原版路线把真实字放入工作栈 0、1；原版 `CodeParametersProgram.fullCommand` 的 **1,499 个含 HALT 的本地标签**在 **8 寄存器／77 栈**执行，又通过原版 `regs8/stacks77` 映射在**40 寄存器／896 栈**执行，并对照整个本地状态。

| 参数流程 | 原版位指令（各自含 HALT） |
| --- | ---: |
| 之前真实执行的 `canonicalStart` | 7,085 |
| 输入路由（`m`、`B`） | 55 |
| 原版参数核心 | 9,130 |
| 15 项结果保存 | 278 |
| 768 个工作栈清理 | 2,636 |
| **五段单独运行合计** | **19,184** |

数学结果：`gapDenom=1600`、七项参数 `[1,1,1,1,0,0,1]`，其二进制字和一元字分别写入栈 **801–807** 与 **808–814**；`gapDenom` 存在栈 800。清理完成后参数仍在、全部 768 工作栈为空，寄存器复位。整个实际流程峰值已占用**252 位栈数据**。

为了避免把五次各自停机误写成一次完整执行，我们又把原版组成程序连接为一张 **7,201 标签的单一程序**（3,160 个原版 `canonicalStart` 静态位置 + 4,040 个原版 `parameters` 静态位置 + 1 个终止标签），从相同 CNF 物理输入一口气运行：

- **19,182 条实际位指令**，唯一最终停机；**峰值栈数据 252 位**，最长单栈 **26 位**，结束时栈数据 **108 位**。
- 访问了 **6,922 个不同的程序位置**。
- `NativeParametersBoundaryAudit.lean` 双路运行分别执行的原版子程序和单一程序，在累计第 **7,084、7,138、16,268、16,545、19,182** 步核对**全部 40 个寄存器和 896 个栈**，五处均完全一致。同时逐条重新扫描全部 896 个栈验证峰值 252 位。
- 这张单一表由我们独立编写的连接器重定向原版操作码形成；**尚未证明它与 OpenAI 上游完整 `StructuredCalls.compiled` 的每一个位置逐项等价**。这是一个具体未关闭的形式化验收缺口。

## 2. 真正执行两套代码搜索

原版 `NativeCode.searches` 共 **2,018 个含 HALT 静态位置**；它不是只返回数学定理中的存在对象，我们执行了具体原版操作码：

| 源级子程序 | 位指令数 | 本地操作码标签 | 实际结果 |
| --- | ---: | ---: | --- |
| `SparseCodeSearch.graphSearch` | **2,680** | 928 | 正确停机；候选位字为 0 位 |
| `SparseCodeSearch.localSearch` | **5,598** | 668 | 正确停机；候选位字为 5 位 |
| **两次搜索核心合计** | **8,278** | — | 与原版 16×48 核心全状态相同 |

加上两次输入搬运、两个候选保存和两次 48 工作栈清理，8 个独立子阶段总共实际执行 **8,870 条指令**（每段各自含停机）。图结果被真正写入物理栈 **816**，局部代码被写入物理栈 **815**，之后 48 个搜索工作栈全部恢复为空，结果字未丢失。检查覆盖了完整的 16 寄存器和 48 栈本地投影，不仅比较输出字。

这组输入的图维数 `r=0`、图代码度数 `D=1`、局部矩阵只有一行一列，因此不能由上述耗时推断在真实困难实例上的效率。

## 3. 原版 `CodeRowsProgram` 真实序列化

搜索结束后，原版 `NativeCodeAssembly.serialize` 的输入路由复制原版已计算的参数、图矩阵和局部矩阵。随后：

| 源级实际程序 | 位指令 |
| --- | ---: |
| 9 项物理输入路由 | 160 |
| `CodeRowsProgram.command` 16×64 本地源核心（共 739 个静态标签） | **715** |
| 输出路由将栈 12 的结果存入物理栈 777 | 103 |
| 原版 768 工作栈清理 | 2,396 |
| **合计（每段含停机）** | **3,374** |

序列化结果是**13 位**，在栈 777 保存。核心程序的整个 16×64 状态和映射到物理 40×896 的结果一致；清理后所有工作栈为空，图／局部候选也仍保存于栈 816／815。它确实运行了真实行生成指令，没有预制结果。

## 4. 最新发现：最终初始化存在远大于前段的真实成本

在序列化完成的同一个物理状态上，我们开始执行**原版 `NativeLeafPreparation.afterCode`**（共 **119 个含 HALT 的静态位置**）：

- 原版距离参数为 **1,280,000**；模数字宽 **2 位**。
- 原版 `HashGreedyProgram.Initialize.zeroWord` 的实际定义要求构造 **5,120,003 位**的编码初始零候选（不是猜测的输出长度）。
- 在限定 **120,000 条真实位指令**时未停机；已有 **2,110 位**候选，峰值虚拟栈数据 **2,240 位**。
- 在严格限制的 **2,000,000 条真实位指令**时仍未停机；已生成 **35,238 位**候选，峰值数据占用 **35,368 位**，并且此前 13 位的行序列化结果未被修改。

这是实打实的源位操作，不是 Lean 在编译代码时卡住。**完整 `afterCode` 的步数与空间峰值尚未测出**；我们不能线性外推得出精确总开销，也不能跳过这些位指令声称已验证论文的运行时间复杂度。这里的原始候选构造成本可能是向完整求解推进的关键障碍，值得专项研究。

## 5. 严格限制与复现

- **已实测：** 原版固定源指令在本地布尔机器上的数值运算、两次搜索、序列化、数据搬运和清理；独立链接参数流程的 **19,182** 步；原版局部程序到物理内存布局的全状态核验；限定步数的后缀计算。
- **未证明：** 整个 `NativeCodeAssembly.command` 的单一完整指令表与原版编译器逐项等价；完整 `NativeLeafPreparation.command` 完成；完整 `HighQueryProgram`、通用 #SAT 求解；理论 TM2 物理空间与真实时间优势。
- **成本口径：** “峰值栈数据位”只计当前占据的布尔栈内容，**不**包含固定 896 栈管理、代码表、寻址成本或 Linux RSS。Lean 的几秒至几十秒的启动／构造时间也不是位算法的时间复杂度。
